# Kekkai 結界

> **The barrier that thinks and acts.**
> An autonomous agent that runs the evacuation, not just the chat.

Kekkai (結界, "protective barrier") is a hazard evacuation command system. It ingests sensor and citizen reports about a hazard (flood first, wildfire second), models how the hazard spreads, keeps a live versioned hazard perimeter, and runs an AI agent that does the actual response work: it expands hazard zones, issues phased evacuation orders, allocates people to shelters, dispatches rescue teams, and drafts and sends multilingual alerts.

Every action is logged, idempotent and undoable. High-impact actions need human approval.

> **Status:** Planning complete, implementation not started. This README describes the target design. Sections marked *(planned)* are not built yet.

---

## Why Kekkai is different

- **The agent has real side effects.** It changes system state (zones, orders, shelters, teams, alerts), not just replies in a chat box.
- **The LLM never does the math.** Geometry, allocation, scheduling and routing are computed by deterministic algorithms implemented from scratch. The LLM decides *when* to call them, explains the results, drafts human-facing text, and handles messy input.
- **Humans stay in control.** A rule-based risk gate, never the LLM, decides which actions need a supervisor's approval.
- **The geofence is alive.** The hazard polygon is generated by a model, versioned, and re-evaluated as conditions change. Plans and approvals are bound to a hazard version, and stale approvals are voided automatically.
- **The maps are only a canvas.** All geospatial logic is Kekkai's own code.

## Core features *(planned)*

**Agent actions**
- Expand or contract hazard zones
- Issue phased evacuation orders per zone
- Allocate populations to shelters under capacity
- Dispatch and reassign rescue teams
- Draft, translate and send alerts
- Create incident reports
- Undo or supersede any earlier action

**Algorithms (implemented from scratch, tested and benchmarked)**

| Need | Algorithm |
|---|---|
| Hazard spread | Dijkstra wavefront (flood), cellular automata (fire) |
| Perimeter | Marching squares, polygon simplification, union and clipping |
| Who is inside a zone | R-tree with ray-casting point-in-polygon |
| People to shelters | Min-cost max-flow |
| Team assignment | Hungarian algorithm |
| Phased evacuation orders | DAG, topological sort, critical path |
| Evacuation routes | Multi-source Dijkstra with dynamic edge blocking |
| Alert dedup | Bloom filter |
| Sensor anomalies | Sliding window with a monotonic deque |
| Report hotspots | Union-find, DBSCAN |
| Caching | Hand-written LRU |

**Infrastructure concepts**
- Geofencing with dynamic, versioned zones
- Message queues (Redis Streams, consumer groups, dead-letter queue)
- Outbox pattern for reliable action delivery
- WebSockets with per-event sequence numbers and resync
- Multi-layer caching with version-based invalidation
- Rate limiting (token bucket, sliding window, tool-call budget)
- Circuit breaker, retries with backoff and jitter, graceful degradation

**Low-level design patterns**
Strategy, Chain of Responsibility, Command with undo, State, Observer, Factory/Registry, Repository.

## Architecture

```
Next.js dashboard (Google Maps via MapAdapter, approvals, agent feed, voice UI)
        ▲ Socket.IO (rooms per incident)            │ REST (JWT)
        │                                           ▼
Simulator ──HTTP──► GATEWAY (Node / Express / TS)
                    auth + RBAC · rate limiting · Zod validation · Socket.IO fan-out
                        │ XADD                ▲ pub/sub          │ HTTP (approve/resume)
                        ▼                     │                   │
                    REDIS  Streams · cache · rate-limit state · LLM cache
                        │ consumer group                │ consumer group
                        ▼                               ▼
                ENGINE (Python worker)          AGENT (FastAPI + LangGraph)
                sensor fusion, hazard model,    graph, tools, LLM router,
                geofence, polygon versions      risk gate, approvals, executors
                        └──────────────┬────────────────┘
                                       ▼
                           POSTGRES + PostGIS
                           domain data · checkpoints · outbox · audit log
LLM router: Groq (fast) → Nemotron (deep) → Ollama (fallback)
```

The engine and the agent are separate services, so an LLM outage never stops hazard tracking.

### Agent flow (LangGraph)

```
gather_context → triage → plan_tools → validate_plan → risk_gate
    ├─ Tier 0/1 (auto) ────────────────────────► execute
    └─ Tier 2 → approval_interrupt ─┬─ approved → stale_check → execute
                                    └─ rejected → replan
execute → verify → summarize → END
```

**Risk tiers**
- **Tier 0 (auto):** notify supervisors, log incident, update report
- **Tier 1 (auto with cooldown):** advisory alerts, team pre-positioning
- **Tier 2 (human approval):** evacuation orders, large zone expansions, road closures

If every LLM provider fails, a deterministic planner runs the same algorithms under a fixed policy and proposes to a human.

## Tech stack

| Layer | Technology |
|---|---|
| Frontend | Next.js, React, TypeScript, Tailwind, shadcn/ui, Zustand, TanStack Query |
| Maps | Google Maps JS API (display only, behind a `MapAdapter`) |

| Agent | Python 3.12, FastAPI, Pydantic v2, LangGraph, Postgres checkpointer |
| Engine and simulator | Python |
| Algorithms | `kavach_algo` style pure-Python package (no I/O) |
| LLMs | Groq API (fast path), Nemotron via Hugging Face (deep path), Ollama (fallback) |
| Voice | Web Speech API, faster-whisper, Piper, optional Sarvam AI |
| Database | PostgreSQL + PostGIS |
| Queue and cache | Redis (Streams, Lua scripts, pub/sub) |
| Testing | pytest, Hypothesis, pytest-benchmark, Vitest, Playwright, k6 |
| Observability | OpenTelemetry, Prometheus, Grafana, Loki, Langfuse (self-hosted) |
| Tooling and CI | uv, pnpm, Ruff, mypy, ESLint, Docker Compose, GitHub Actions |

Everything is free or open source except Google Maps, which requires a billing account. Protect it with API restrictions, daily quotas and budget alerts.

> Verify current model names, tool-calling support and rate limits for Groq and Nemotron in their official docs before relying on them.

## Getting started *(planned)*

Prerequisites: Docker, Node.js 20+, pnpm, Python 3.12, uv.

```bash
git clone https://github.com/<you>/kekkai.git
cd kekkai
cp .env.example .env        # add GROQ_API_KEY, HF token, Google Maps key
make up                     # start Postgres, Redis and all services
make seed                   # load a demo scenario
make demo                   # run the flood simulation
```

Open `http://localhost:3000` for the dashboard.

Other commands: `make test`, `make bench`, `make lint`, `make down`.

### Environment variables

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | Postgres connection |
| `REDIS_URL` | Redis connection |
| `GROQ_API_KEY` | Groq fast-path LLM |
| `HF_TOKEN` | Hugging Face access for Nemotron |
| `OLLAMA_BASE_URL` | Local fallback LLM |
| `NEXT_PUBLIC_GOOGLE_MAPS_KEY` | Map rendering (restricted key) |
| `JWT_SECRET` | Token signing |
| `SARVAM_API_KEY` | Optional voice and translation |

Configuration is validated at startup, and services fail fast on missing or invalid values.

## Safety model

1. The LLM never computes geometry, allocations or routes.
2. The LLM never approves Tier 2 actions.
3. Sensor data, reports and user text are treated as untrusted input.
4. Approvals are bound to a hazard version and expire if the hazard changes.
5. Every action is idempotent, logged and reversible where possible.
6. If the agent is uncertain or degraded, it proposes to a human instead of acting.

Kekkai is a portfolio and learning project running on simulated data. It is **not** a certified emergency system and must not be used for real-world evacuation decisions.
